# صنعة 2 — بوابة التقارير الأسبوعية المباشرة

هذا المستودع نسخة مطورة من مشروع `redouane-itp/san3a-2`.

## العمل اليومي

1. يفتح ممثل المؤسسة الموقع، ويسجل بحسابه (البريد الإلكتروني وكلمة المرور).
2. بعد اعتماد الحساب، يحدد الأسبوع والتاريخ، ويدخل بيانات التخصصات الثلاثة جداولها.
3. يستعمل **حفظ مسودة** للعودة لاحقاً. يمكن الحفظ التلقائي عندما يكون الأسبوع والتاريخ محددين.
4. عند اكتمال البيانات يضغط **اعتماد وإرسال التقرير**. ينتقل التقرير إلى قاعدة البيانات وتراه الإدارة في لوحتها.
5. في حالة الخطأ بعد الإرسال يمكن للمسؤول **إعادة فتح التقرير للتعديل**.

لا حاجة إلى Gmail أو تنزيل ملفات وإرسالها باليد.

## ما نُفذ

- واجهة عربية من اليمين إلى اليسار ومناسبة للهاتف والحاسوب.
- تسجيل ودخول بالبريد وكلمة المرور باستخدام Supabase Auth.
- طلب انتساب لمؤسسة، ومراجعة الحسابات من المدير قبل تفعيل الوصول.
- نماذج الجداول الثلاثة ومؤشرات الحضور والإنجاز.
- حفظ تقارير كل مستخدم في قاعدة بيانات مشتركة؛ إغلاق التقرير بعد الإرسال.
- لوحة إدارة للاستعراض والاعتماد والتصفية، تتحدث عبر Supabase Realtime.
- سياسات Row Level Security بحيث لا يرى الموظف تقارير غيره.
- الاحتفاظ بالاستمارة المحلية القديمة في `استمارة_محلية_محدثة.html`.

## تفعيل الموقع (خطوات إدارية لمرة واحدة)

### 1. GitHub Pages

افتح `Settings → Pages` في مستودع `scientifica007/san3a-2`، واختر `Source: GitHub Actions`.
انتظر ظهور تنفيذ ناجح لسير العمل `Publish San3a 2 live portal` في `Actions`.
يكون عنوان الموقع بعد نجاح النشر:

https://scientifica007.github.io/san3a-2/

### 2. إعداد Supabase Auth

الموقع مربوط بمشروع Supabase الحالي:
`uxtsyzyotnohxvopgcmh`. أُنشئت الجداول الجديدة بعزل الأسماء:
`public.san3a_profiles` و`public.san3a_reports`.

من لوحة المشروع افتح `Authentication → URL Configuration`:
- **لا تغيّر Site URL الحالي**، لأن مشروع Supabase مشترك مع تطبيقات أخرى.
- في `Redirect URLs` فقط أضف `https://scientifica007.github.io/san3a-2/`.
- احفظ التغيير، ولا تحذف عناوين التطبيقات الأخرى.

**ضروري قبل تسجيل عموم مستخدمي المؤسسات:** تفعيل خدمة إرسال بريد SMTP مخصصة من
`Authentication → SMTP Settings`.
خدمة Supabase الافتراضية لا ترسل إلى عناوين غير مصرح بها/خارج فريق المشروع.
لا تلغِ تأكيد البريد كحل دائم، ولا تنشر أي مفتاح `service_role` في ملفات الموقع.

### 3. تعيين المسؤول الأول

يسجل المسؤول الذي ستعتمد عليه في الموقع بكتابة بريده وكلمة مرور؛ ثم يؤكد بريده.
بعد إنشاء ملفه (صف في `san3a_profiles`) ينفذ مالك قاعدة البيانات عبر SQL Editor
**مرة واحدة فقط**، بعد تغيير `ADMIN_EMAIL_HERE` إلى البريد الفعلي للمسؤول:

```sql
update public.san3a_profiles
set role='admin', status='active', institution_name=null
where lower(email)=lower('ADMIN_EMAIL_HERE');
```

يجب أن تكون نتيجة تحديث الصفوف صفًا واحدًا بالضبط.
بعد ذلك يُسجل المسؤول الخروج ثم الدخول مجددًا، فتظهر لوحة الإدارة.
**لا تمنح صلاحية الإدارة تلقائيًا لمجرد التسجيل أو مطابقة بريد المستلم السابق.**

### 4. اعتماد الموظفين

يختار الموظف المؤسسة عند إنشاء حسابه. ثم يقوم المسؤول باعتماد حسابه بعد التحقق من هويته.
يمكن للموظف مشاهدة تقاريره فقط، بينما يشاهد المسؤول كل الحسابات والتقارير.

## تنبيه تشغيلي

- الرسائل تحتاج مزود SMTP صالحًا. من دونه قد يفشل تأكيد البريد لمستخدمي المؤسسات.
- واجهة الموقع ملفات ثابتة؛ قاعدة البيانات وتسجيل الدخول يعملان عبر Supabase.
- "مباشر" يعني ظهور تحديثات التقارير عبر Realtime أثناء اتصال المستخدمين. إن انقطع
  الاتصال يمكن استعمال زر **تحديث البيانات**.
- هذا الإصدار أولي؛ يلزم اختبار تسجيل مستخدم فعلي، واعتماده، وإرسال تقريره قبل الإعلان
  عن جاهزية التشغيل الميداني الواسع.

## الخصوصية

تم تفعيل RLS على الجداول الجديدة ولم يُنشر سوى المفتاح العمومي `publishable`.
جداول التفتيش السابقة لا يُعدلها هذا المشروع.
